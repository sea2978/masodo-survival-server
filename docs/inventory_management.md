# Inventory management (0.8.9 / protocol 13)

Equipment cards in the inventory popup offer discard and dismantle with a confirmation. Discard removes the chosen copy. Dismantle returns exactly the recipe's direct ingredients (including intermediate equipment and consumables). Recipes and returns appear before confirmation. Capacity and unique-material ownership are checked before removing anything; failed returns leave the entire inventory intact. Equipment stats update on the server. Consumable discard clears the entire chosen stack, freeing one slot. No extra action time is charged for inventory management, and queued actions block changes.

For a human client advertising `inventory_choice_v1`, finding a new consumable type with all three slots full creates a persisted `pendingPickup` instead of losing the reward. Its modal offers each existing stack as a replacement, or discarding the discovery. Replacing clears that full stack and grants the discovery in one server transaction. Identical consumables stack normally without the dialog. The server requires the current pickup token, rejects repeated/stale choices and blocks subsequent timed actions until resolution. Reconnect restores the choice; death and match end clear it. AI and older clients retain their previous full-slot behavior.

`npm run test:inventory` tests actual search completion, replacement/decline/merge, all equipment recipe returns, failed-return rollback, unique ownership, stats, room persistence, deltas, resume and UI event state with DOM mocks. UI mock tests do not assert browser appearance.
